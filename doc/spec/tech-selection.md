# E. 技術選定（ドラフト）

このドキュメントは、実装言語をRustとした場合の主要依存（SQLite / フィードパース / YAML / テスト）を選定するための叩き台なのだ。

## E0. 前提

- 実行形態はまずCLI Mode（都度実行）を基本とし、RPC Modeは将来拡張として扱うのだ。
- 永続化はSQLite（`doc/db.dbml` が正本）で、整合性は基本DB制約とトランザクションで担保するのだ。
- 「更新（sync）」は単一writerとして扱い、並行書き込みでスケールさせる設計は当面不要なのだ。

## E1. 選定方針

- **依存は最小**：MVPで必要なものだけを入れるのだ。
- **境界で閉じる**：DB/HTTP/パーサの型やエラーをアプリ層に漏らさず、後から差し替え可能にするのだ。
- **SQLを一次資産にする**：クエリはSQLとして管理し、ORM前提にはしないのだ。
- **将来の運用差分を吸収**：CLI単発と常駐RPCの差は「I/Oの駆動（sync/async）」に閉じ、ドメインロジックは共通化するのだ。

## E2. SQLiteアクセス

### 推奨（MVP）

- `rusqlite`
  - CLI単発・同期I/Oが中心なら最も単純で、依存も読みやすいのだ。
  - 将来のRPC化を見ても「DB操作を専用スレッドに直列化（DB actor）」する構成なら、そのまま継続しやすいのだ。

### 代替（RPCや非同期を強く想定する場合）

- `sqlx`（Sqlite）
  - tokioベースの常駐サーバや、HTTP取得などI/Oを非同期で統一したい場合に整合しやすいのだ。
  - ただし、SQLiteは単一writerである点は変わらないので、**非同期＝DB書き込みの並列化**ではないのだ（主に「同時読み取り」や「I/O待ちの隠蔽」のためなのだ）。

### マイグレーション

- 方針としては「SQLファイルを並べて適用」できる仕組みを採用し、DBライブラリから独立させるのが安全なのだ。
  - `refinery`（SQL migration）
  - `rusqlite_migration`（rusqlite向け）
  - `sqlx::migrate!`（sqlxを採用する場合）

## E3. フィードパース（RSS/Atom/JSON Feed）

- RSS/Atom：`feed-rs`
  - パース結果を「内部の正規化モデル」に変換してDBへ入れるのだ（ライブラリの構造体をDB層まで通さないのだ）。
- JSON Feed：`jsonfeed`（もしくは `serde` による自前デコード）
  - JSON Feedは仕様が比較的素直なので、serdeで最小限の構造体を定義して正規化しても良いのだ。

注：エッジケース（文字コード、壊れたXML、日付パースの揺れ）への耐性は実装品質に直結するので、MVPでは「壊れた入力はスキップしてログに残す」方針を明確にするのだ。

## E4. YAMLパース（`feeds.yaml`）

- `serde` + `serde_yaml_ng`
  - `serde_yaml` はメンテ状況の観点で避け、後継の `serde_yaml_ng` を前提にするのだ。
  - feeds.yamlは「ユーザー編集する設定」なので、エラーメッセージ（行番号・キー名）を重視するのだ。

## E5. テスト環境

### ユニットテスト

- Rust標準の `#[test]` を基本とし、ドメインロジックは副作用を切ってテストしやすくするのだ。
- パラメタライズが必要なら `rstest` を採用候補にするのだ。

### CLI統合テスト（推奨）

- `assert_cmd`：CLIを実際に起動してexit code / stdout / stderrを検証するのだ。
- `predicates`：出力の部分一致・正規表現マッチを扱うのだ。
- `tempfile`：一時ディレクトリ + テスト用SQLiteファイルを安全に作るのだ。
- 仕様の出力が固まってきたら `insta`（snapshot）を検討するのだ（ただしスナップショット濫用は避けるのだ）。

### HTTP取得のテスト

- 同期実装なら `httpmock`、非同期（tokio）なら `wiremock` を候補にするのだ。
- 重要なのは「ETag/Last-Modified等の高度なキャッシュ」より、MVPでは「タイムアウト・リトライ・失敗時の扱い」をテストすることなのだ。

## E6. 乗り換えを安くする設計メモ

- `Store`（Repository）境界を定義し、DBライブラリの型（Row/Pool/Error）を外に漏らさないのだ。
- DBは以下を最小APIとして扱うのだ（例）：
  - `upsert_feed(...)`
  - `upsert_entry_batch(...)`
  - `list_entries(query, paging)`
  - `set_tags(entry_ids, tags)`
- RPC Modeを見越す場合でも、まずは「更新中も読み取り可能（WAL）」と「更新はトランザクション一括」を優先するのだ。

## E7. 未決事項（後で決める）

- FTS5（全文検索）：日本語トークナイズの設計が必要なのでPhase拡張とするのだ。
